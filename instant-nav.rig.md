# instant-nav rig: dariah-website

- BUILD: local production build, `EXPOSE_TESTING_API=1 bun run build`, served with `EXPOSE_TESTING_API=1 bun run start` (`next start`). No CI or preview deploy is configured yet; this is a local-only rig.
- EXPOSE: `experimental.exposeTestingApiInProductionBuild` in `next.config.ts` is wired to `process.env.EXPOSE_TESTING_API === "1"`. The variable must be set for `next start` too, not only `next build`: `next start` re-evaluates `next.config.ts`, and the page runtime reads the flag from that runtime config. Without it, client-side navigations still lock (the flag is baked into the client bundle), but initial-load (`page.goto`) locks silently no-op and those tests pass vacuously. Do not set `E2E_TEST_PROXY=1` (next's test proxy, `experimental.testProxy`) for this server: the proxy disables the incremental cache in `next start`, so no prerendered page is served from the build and `instant()` tests fail - see `tasks/05-e2e-known-issues.md`. The `next.onFetch` tests skip without it. Only set for the local production build used to run `instant()` tests; never set for a real deploy.
- RUN: `playwright test --config ./e2e/playwright.config.ts` against `NEXT_PUBLIC_APP_BASE_URL` (from `.env.local`, defaults to `http://localhost:3000`). The config's `webServer` runs `bun run dev` outside CI, but `reuseExistingServer: true` means: start the production server manually first (`EXPOSE_TESTING_API=1 bun run build && EXPOSE_TESTING_API=1 bun run start`), then run `playwright test` — it reuses the already-listening production server instead of spawning `next dev`. Never trust an `instant()` result captured while `next dev` owns the port.
- TEST USER: none. This is an unauthenticated public content site (events, news, projects, network, spotlight) — every route under test renders the same for every visitor, so there is no login/session/storageState to set up.
- DRIFT: none identified — no feature flags, plans, roles, or A/B buckets in this app. The only per-request variance is live CMS data (event lists, news items) returned by the knowledge-base API, which does not gate the shell markers under test.
- PORT: if port 3000 is taken (e.g. by your own `next dev`), run both the server and playwright with `PORT=3100` (or any free port): `.env.local` derives `NEXT_PUBLIC_APP_BASE_URL` from `${PORT:-3000}`, and the playwright config reads it. Do not stop a server you did not start.
- LOOP: local build → start → test, fully agent-drivable on one machine; nothing to push, no deploy wait, no secrets beyond the existing `.env.local` (`API_ACCESS_TOKEN`, `TYPESENSE_ADMIN_API_KEY`) already required for any build. Stop any process already on the configured port before starting the production server; fail loudly on `EADDRINUSE` rather than reusing an unrelated process.
- LIVENESS: n/a — local `build && start` always measures the artifact just built.
- WALLS: `next build` (unlike `next dev`) eagerly scans next-intl's `srcPath` (`./app`, `./components`, `./lib` — `configs/i18n/messages.config.ts`) for message extraction; the repo has no `components/` directory, so a clean checkout fails `next build` with `ENOENT: scandir .../components` before any route is touched. Workaround: create an empty `components/.gitkeep` so the scandir succeeds. This is a pre-existing build-only bug, unrelated to Cache Components; worth fixing upstream (either add the directory or drop it from `srcPath`) so `next build` isn't broken on a fresh checkout.
